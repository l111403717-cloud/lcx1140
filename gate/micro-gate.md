## Harness 门禁（Micro-Gate）
1. 纯问答/只读分析不判级。要改代码时先输出一行：`[HX T0|T1|T2 · 理由]`。
2. T0 = ≤2 个文件、无依赖/配置/接口变更、单会话完成；或**常规前端构建与静态文件上传/同步（不改动服务器底座配置与数据库）** → 直接做，改后跑 `hx verify --quick` 或仅作目标页面联通核验。
3. 命中任一条即先加载 skill `harness-architect`，由它决定是否需要 PLAN/状态文件：≥3 文件或跨模块；改依赖/系统配置/数据库/鉴权/重大生产架构发布（常规静态同步除外）；需跨会话接力；用户说“重构/大改”。
4. 日常上传减负原则：普通上传/同步只做“打包 + 增量上传 + 目标页面冒烟核验”，无明确报错严禁地毯式扫描本地代理（Clash/Mihomo）、严禁深挖服务器历史软链接与无关系统配置。
5. T0 执行中实际触及 >2 文件（非构建产物），或验证连环报错 → 立即停下，加载 skill 重新判级，不得继续以 T0 名义推进。
6. 红线：不删/改/注释/skip 既有测试与断言；不改验证命令、lint、tsconfig 规则来“变绿”；不用吞异常、硬编码返回值、`|| true` 冒充通过。
7. 临时脚本、日志、状态只写 `.harness/` 或系统临时目录，禁止落在项目根目录。
8. 不回滚、不覆盖用户已有的未提交改动；要改到这些文件时先告知。
9. 宣称“完成/通过”必须附上实际命令和退出码；没跑就写 NOT_RUN，不得推测为通过。
10. `hx` 不可用或项目没有工具链时，按降级链自查：typecheck → lint → build → 冒烟运行 → diff 范围审计，并逐项注明结果。
11. 开工前：若存在 `.harness/PLAN.md`，先跑 `hx handoff --check`：FRESH → 按其“接力 Prompt”执行，不重复询问“已确认决策”；STALE → 先 `hx verify` 再继续。若存在 `PROJECT_MAP.md`，改代码前按它定点读取，禁止全盘扫描。
12. 用户说“交接/换会话”，或会话结束时仍有未完成项 → 运行 `hx handoff` 并补全交接块；一次做完且已验证的任务不写交接。
