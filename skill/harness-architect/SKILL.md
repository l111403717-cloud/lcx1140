# Skill: harness-architect (v2.3 · 通用减重版)

## 核心设计理念：快速实施、按需设闸、证据验收
本技能用于在复杂软件工程中建立防跑偏、可验证、可跨会话接力的受控开发闭环。
与 `map` 技能联动：已有地图先复用并只核对当前涉及的路径；缺失时允许定点探索，只有架构不清确实阻碍实施或用户明确要求时才建图。地图、PRD、状态文件不是普通开发的开工前提。

默认直接推进用户已授权的实现，不把“用了 Harness”理解为必须走重型流程。单模型可独立完成；多模型协作只是可选执行方式，不是本技能的前提。优先尽早打通可测试的纵向功能，再继续完成已约定的其余范围；阶段成果不等于全部完成。

## 1. 最高优先级契约（铁律红线）
1. **轻量分级**：判断当前任务适合快速直做、轻量委派还是持久接力；仅在启用 Tier 1/2 时记录状态。不为每个普通任务运行状态机。
2. **规划服务于实施**：目标、边界与验收已明确时直接开工；Tier 1 只需短计划，Tier 2 复用已有需求与地图，仅补缺口。用户要求完整 Harness 不等于要求重建全部文档，不强制 `map -> PRD -> Harness` 串行准备。
3. **控制文件有边界**：Harness 专属计划、状态与临时脚本通常放在 `.harness/`，并遵循项目现有约定；正常交付文档或用户明确要求的文件不强行塞入该目录，也不为流程额外制造根目录辅助脚本。
4. **单一事实源（SSOT）**：启用持久 Harness 时，`.harness/state.json` 记录机器状态，`.harness/PLAN.md` 记录任务约定与接力信息；未启用时不创建占位文件。
5. **验证可信（不冒充物理隔离）**：禁止为伪造通过而跳过测试、弱化断言或硬编码成功。常规任务靠实际 diff 与真实验证；仅高风险或用户明确要求固定验收契约时，对选定验证文件计算 SHA256，不默认锁整个工具链。
6. **保护用户已有修改**：只检查当前相关路径的未提交修改，不回滚用户代码、不因工作区脏而停工。轻量模式在内存保留基线；Tier 1/2 才在已有状态中记录相关基线，不展开无关未跟踪目录，不强制为全库计算 diff 哈希。
7. **权限与范围诚实**：提示词、白名单和状态文件不是文件权限隔离。明确目标范围和必要验证后即可进入 READY；只有真实权限、需求或高风险条件未满足时才阻塞，不为了凑齐仪式性文件而禁止实施。

### 1.1 边界保护（仅在相关情形启用）
1. **按实际风险升档**：不因文件数、跨目录或一次测试失败自动升级。只有发现不可逆副作用、关键接口风险、真实交接需要或范围明显失控时才提高控制强度；保留已有成果，不重跑全部准备步骤。
2. **允许正常维护测试**：在授权范围内可新增或修正测试、构建入口及依赖声明；修改现有断言须对应真实需求变化并审查理由，不能为了变绿而削弱覆盖。可疑删除、跳过或仅运行单例须核查，不把所有合理测试修改一律判为作弊。已明确锁定的验收契约须先说明变更并获得授权。
3. **按需保护重叠修改**：将覆盖已有未提交内容且难以精确恢复时，才备份受影响文件到 `.harness/snapshots/`；普通可审查的局部补丁无需批量备份。失败不自动恢复整个快照；仅撤销本次确认的改动，避免抹掉期间其他人的编辑。
4. **地图锚点保鲜校验（Map Freshness Check）**：使用项目所在平台的原生方式确认地图中涉及的目标路径存在。若发现路径漂移或地图过期，仅针对当前关联子目录定位并修正；仅在本任务已使用 PLAN 时记录，不因此创建全套文档。

## 2. 前置风险分级路由（Tiered Fast-Track）
- **Tier 0 (Fast-Track，默认)**：只读分析、文档修改、普通功能与可逆的局部重构。快速确认目标、相关已有修改与验证方式后实施；不要求 PRD、建图或持久状态。文件数量不是门槛，只读任务也不强制跑无关测试。
- **Light Delegation (可选轻量委派)**：有授权且有净收益时，可将实现量较大、边界清楚的单一编码子任务交给更快的子代理，即使任务不能并行；重复或可独立并行的工作也适合委派。主代理负责验收；协调和上下文成本大于收益时直做，不创建完整控制文件。
- **Tier 1 (Standard)**：确实需要阶段记录、持续追踪或交接的任务。创建/复用精简 `.harness/PLAN.md` 与 `.harness/state.json`；需求已清楚时不额外写 PRD。
- **Tier 2 (Heavy Relay)**：影响多个核心模块且难以回滚的架构变更、高风险不可逆变更，或用户明确要求完整接力。保留必要的模块边界、风险检查和验收证据；跨模块或“架构”标签本身不自动触发 Tier 2。

默认选择足够用的最轻级别。准备完成一次就进入实施；没有新证据不要重新分级、重建地图或重复基线检查。遇到高风险先限制相关操作，不必停止其他安全且独立的工作。

## 3. 原生工具链自适应契约（Native Toolchain Adapter）
按项目根目录特征文件自动映射原生探针与验证器，严禁强绑 Python：
1. Node/TS (`package.json`)：`node -v` + `npm/pnpm/yarn/bun run <typecheck|lint|test|build>`
2. Rust (`Cargo.toml`)：`cargo --version` + `cargo check` / `cargo test`
3. Go (`go.mod`)：`go version` + `go vet ./...` / `go test ./...`
4. Python (`pyproject.toml`/`requirements.txt`)：`python3 --version` + `pytest` / `ruff` / `pyright`
5. 通用构建 (`Makefile`/`Justfile`/`Taskfile.yml`)：优先调用已定义的 `check` / `test` / `verify`
6. 复用已知可用环境，不为每阶段重复查版本。无现成验证器时选择最小有意义的检查，并如实标明覆盖；确需控制脚本时才放入 `.harness/`，不为了满足门禁制造没有验证价值的探针。

## 4. 持久接力流程（仅 Tier 1/2）
普通快速任务和轻量委派不创建 Harness 文件，也不逐项播报状态机。确需跨会话追踪时，采用最小闭环：
1. **计划**：确认结果、非目标、负责模块、风险和一条主要验收方式；复用已有地图、计划与基线，只补真实缺口。
2. **实施**：尽快开始，不要求先做通用环境盘点。按模块推进；阶段通过后继续完成剩余约定范围，不把一个局部切片误报成全部完成。
3. **验证**：查看本次真实改动和相关用户既有改动；先运行聚焦测试，再按风险运行集成/构建验证。需要交接时，状态记录目标、已改内容、证据、未完成事项与下一步。
4. **交付/阻塞**：全部范围与必要检查完成才标记交付。外部依赖失败时，保留已有本地进展，继续独立可做的部分，并准确标出未验证项；只有确实不能安全前进时才阻塞。

### 4.1 执行、返工与等待预算
- 信息足够时直接开始，不设置固定的“准备时长”或等待仪式；只有存在具体未知点时才继续定点调查，并在没有新证据时停止重复准备。
- 首轮实现后先跑定向验证；共享接口/依赖受影响或最终交付时按需跑回归/构建。源码、环境、验证契约未变时复用同一份证据，不反复执行相同检查。
- 同一失败链默认只做 1 次针对性修复，包含主代理修复、子代理返工和应用内模型调用修正；若出现新证据、明确的新修复路径且预计收益高于再调用一次模型的成本，可再尝试 1 次。不重复同一方案，也不按层叠加次数。
- 外部模型/网络相同错误最多主动重试 1 次，不叠加已有 SDK/宿主重试；先核对已有调用是否仍在运行，避免重复请求。失败后隔离不可用环节，继续可独立完成的本地工作，真实调用未成功就标未验证。
- 不要为了委派而主动制造失败、重复跑探针或嵌套启动整套 CLI；只有用户明确要求回归/故障演练时才这样做。
- 优先使用已有等待/异步完成机制，避免 `sleep + ps + 读输出` 高频轮询。不要为委派或验收随意嵌套启动整套 CLI；只有目标产品确实依赖该集成链路且已授权时才测试，并优先用本地 fixture 隔离验证。
- 上下文长时仅保留目标、当前改动、验证证据和下一步，不把全部历史重复塞入每次调用。压缩次数不触发重新规划，也不声称自动切换了新对话；需要真实交接时写精简接力点，遵守宿主能力和用户授权。

## 5. 双核文件规范（仅 Tier 1 & Tier 2 创建）
- 仅在 Tier 1/2 确需持久追踪时使用 `.harness/PLAN.md` 与 `.harness/state.json`，保留本任务真正需要的字段；不要求填满模板字段或每次命令后更新。
- `PRD.md` 仅在需求尚需结构化拆解、跨模块决策或用户明确要求时新增；已有需求文档优先复用。
- Harness 控制文件和辅助脚本放在 `.harness/`，不把临时控制代码散落到项目根目录。历史文件可作参考，但不自动视作当前事实源；先核验其是否仍被项目使用。

## 6. 汇报规范（简洁、以交付为中心）
- 开始时一句话说明目标与必要边界，随后执行；不要逐工具播报状态机。
- 有实际进展、长等待、范围变化或真实阻塞时才更新：做成了什么、卡在哪里、接下来做什么。只有需要用户决策时才提问，不在每阶段等确认。
- 最终简报：完成范围、实际验证结果、未完成/未验证项。部分可用不能声称全部 PRD 已完成；没有测试证据不能写 PASS/DELIVERED。
- Tier 1/2 只在阶段完成、失败、交接时更新状态与简短证据；不强制输出大面板或每次工具调用落状态。
