# Harness：按需加载入口

## 1. 必要约束
- 优先完成用户已确认的全部范围。最小可用闭环只决定实施顺序，阶段成果不等于全部完成；已有需求和决定直接复用。
- 目标、边界与验收明确后直接实施；不为流程额外建图、写 PRD、备份全仓或运行状态机。只查看当前相关路径的 Git 状态和差异，保留用户已有修改，不因工作区脏而停工；普通基线在内存保留，确需还原时才做定点快照。
- 使用足够用的最轻控制级别。文件数、跨目录或一次失败触发重新判级，不自动要求持久文件或 Tier 2；发现真实风险时只限制相关操作，继续独立可做的工作。
- 提示词、白名单和状态文件不是权限隔离。部署、生产写入等操作须有对应授权，已有授权不重复询问；单模型可以独立完成，委派仅在有授权且有收益时使用。
- 查看真实改动，按风险做有意义的验证；不得跳过测试、弱化断言或硬编码成功来冒充通过。证据仍有效时复用，不重复扫描和验证。
- 开始时简述目标与必要边界，有实际进展或阻塞时再更新。最终说明完成范围、实际证据和剩余项，不用流程播报替代实施。

## 2. 轻量分级
- **Tier 0，默认**：只读分析、文档修改、普通功能与可逆局部重构；确认相关已有修改和验证方式后直做，不创建 PRD、地图或持久状态。
- **轻量委派，可选**：有授权且边界清楚的实现子任务可委派；主代理核对真实 diff 和验收证据，协调成本较高时直做，不创建完整控制文件。
- **Tier 1**：确需阶段追踪或交接，创建／复用精简 PLAN 和 state；不额外重写已明确的需求。
- **Tier 2**：多个核心模块且难以回滚的架构变更、高风险不可逆变更，或用户明确要求完整接力；保留必要边界和证据，不重新制造整套准备材料。

## 4. 推进与收尾
- 已有 `.harness/PLAN.md` 时，在继续业务实施前按交接参考核对状态，复用已确认决定；已有 `PROJECT_MAP.md` 时按相关路径定位，只有漂移或缺口才定点补查。不因没有地图而阻塞普通开发。
- 只在 Tier 1/2 确需持久追踪时使用 `.harness/PLAN.md` 与 `.harness/state.json`；控制脚本和临时材料遵循 `.harness/` 及项目约定，正常交付文件不强行放入其中。
- 实施、验证、继续剩余范围；局部受阻不停止其他可做项。需要真实交接时按参考保留目标、改动、证据、剩余项和可执行的下一步；一次完成且验证通过的任务不写交接。

### 4.2 完整范围验收与完成判定
- 目标模式必须实际登记交付结果、需求来源及完成条件，并核对保存结果；完整 PRD 的应交付项须逐项核对，不自行删项或缩成演示版。具体登记、范围与证据规则按需读取验收参考。
- 每次准备停止或标记完成前，核对全部本轮应交付项。仍有已授权且可独立推进的工作时继续；不把构建成功、上线或抽样通过当作完整验收，也不逐阶段等待批准。
- 全部本轮应交付项达到约定标准，才可宣称完整完成或标记 `complete`／`DELIVERED`。未交付或关键未验证项如实保留；局部缺资料、外部失败、预算耗尽及运行中断均不等于完成，状态操作遵守宿主契约。
- 验收与实际风险相称，区分检查已执行与不可控外部结果已达成。不编造证据、不降低标准、不以无关检查拖延收尾。
