# 持久计划与跨会话交接

已有 `.harness/PLAN.md`、决定启用 Tier 1/2，或确实需要交接时读取。普通快速任务不因此创建计划或状态文件。

## 4. 持久接力流程（仅 Tier 1/2）
普通快速任务和轻量委派不创建 Harness 文件，也不逐项播报状态机。确需跨会话追踪时，采用最小闭环：
1. **计划**：确认结果、非目标、负责模块、风险和一条主要验收方式；复用已有地图、计划与基线，只补真实缺口。
2. **实施**：尽快开始，不要求先做通用环境盘点。按模块推进；阶段通过后继续完成剩余约定范围，不把一个局部切片误报成全部完成。
3. **验证**：查看本次真实改动和相关用户既有改动；先运行聚焦测试，再按风险运行集成/构建验证。需要交接时，状态记录目标、已改内容、证据、未完成事项与下一步。
4. **交付/阻塞**：按 [完整范围验收](acceptance.md) 核对完整范围与验收证据，决定继续、交付或保留接力；不以阶段成果结束整个任务。

## 5. 双核文件规范（仅 Tier 1 & Tier 2 创建）
- 启用持久 Harness 时，以 PLAN 记录任务约定与接力信息，以 state 记录机器状态；未启用时不创建占位文件。
- 仅在 Tier 1/2 确需持久追踪时使用 `.harness/PLAN.md` 与 `.harness/state.json`，保留本任务真正需要的字段；不要求填满模板字段或每次命令后更新。
- `PRD.md` 仅在需求尚需结构化拆解、跨模块决策或用户明确要求时新增；已有需求文档优先复用。
- Harness 控制文件和辅助脚本放在 `.harness/`，不把临时控制代码散落到项目根目录。历史文件可作参考，但不自动视作当前事实源；先核验其是否仍被项目使用。

## 7. 导航与接力（Map + Handoff）

### 7.1 开工导航
1. 存在 `.harness/PLAN.md` → 跑 `hx handoff --check`：
   - `FRESH`：直接执行 Handoff 段里的“接力 Prompt”第一步；“已确认决策”视为既定事实，不再询问。
   - `STALE`：代码在交接之后被改过，先跑 `hx verify` 刷新证据，再继续。
   - `INCOMPLETE`：上一棒没写完，按现有内容加 `git diff` 推断进度，并向用户确认一次。
2. 存在 `PROJECT_MAP.md` → 只按地图定位目标文件；地图没覆盖到的才做定点搜索。若 `hx map-check` 报 `STALE`，只修正当前任务相关的段落，不重建整张地图。
3. 没有地图 → 小任务定点探索即可。只有 Tier 1/2 任务或架构确实不清楚时，才**建议**用户运行 `/map`，不擅自建图。

### 7.2 何时写交接（满足任一条件）
- 用户说“交接 / 换会话 / 下次继续”；
- Tier 1/2 在阶段结束时仍有未完成项；
- 上下文已明显过长，需要换会话。

一次做完且验证通过的任务**不写**交接，最终汇报即可。文件数不是触发条件。

### 7.3 怎么写
1. 先跑 `hx verify`，让证据指纹与当前代码一致；再跑 `hx handoff`。脚本会在 `.harness/PLAN.md` 的 HANDOFF 标记块里生成骨架，并自动填好：时间、指纹、改动文件、验证证据。
2. AI 只替换骨架里的 `TODO(agent)` 占位符，补全 ① 每个文件一句话改动摘要、③ 已确认决策、④ 未完成与风险、⑤ 接力 Prompt。
3. **禁止手写或改写“② 验证证据”**。证据显示 STALE 时，如实保留，不得改成 PASS。
4. 写完跑 `hx handoff --check`，结果必须是 `FRESH`。交接块覆盖写入，只保留最新一份，总长 ≤ 40 行。
5. 接力 Prompt 必须是下一位 Agent 可以直接执行的第一步，写明要读哪个文件、跑哪条命令、改哪个点、不要碰哪里。
