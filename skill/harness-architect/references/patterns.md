# 通用智能体协作架构模式 (6 Architecture Patterns)

本项目提取自工业级智能体架构实践，用于为不同开发任务选择最精简稳健的协作模型。

---

## 1. 生成 - 审查模式 (Producer - Reviewer) —— 【通用默认推荐】
由“主程序员（Coder）”与“严苛质检员（QA Reviewer / Verifier）”结对工作。

```
[用户需求] → [主开发生成代码] → [质检员运行脚本验货] 
                     ↑                     │
                     └── (未通过：重试2~3次) ──┘
```
- **适用场景**：日常功能开发、Bug修复、SQL修改、UI重构；
- **核心规矩**：
  1. 质检员只看确定性脚本输出（编译退出码、测试断言），不听主开发口头解释；
  2. 连续报错 3 次自动触发熔断，保留错误快照并呼叫人类，坚决防止死循环刷 Token。

---

## 2. 顺序流水线模式 (Pipeline)
严格单向推进的阶段性工程。

```
[需求分析] → [架构设计] → [核心实现] → [集成打包]
```
- **适用场景**：从 0 到 1 搭建全新项目、重构大型模块；
- **核心规矩**：上一阶段产物未通过验收门禁前，下一阶段坚决不准启动。

---


### 2.1 Pipeline Relay（多会话接力）

Pipeline 模式默认按“一个模块、一个新会话、一次验收、一次交接”推进。模块状态写入 .harness/PLAN.md，环境门禁证据以 .harness/state.json 与 hx verify 为准。下一模块只能由依赖全部完成的 TODO 模块中选择；当前模块的验收、hx verify 全部通过且 hx handoff --check 确认 FRESH 后才可交接。

适用时使用 AUTO 隔离子代理；宿主不具备隔离上下文时使用 MANUAL，输出完整接力提示词。任何失败、过期证据、范围冲突或信息缺口都停在当前模块并转 BLOCKED，不能调度下一模块。

## 3. 专家池模式 (Expert Pool)
由任务分发器（Task Router）根据修改类型，动态调用特定领域专家。

```
               ┌→ [前端 UI / Compose 专家]
[任务路由] ───┼→ [后端业务 / SQL 迁移专家]
               └→ [底层构建 / 环境运维专家]
```
- **适用场景**：多技术栈混合的大中型项目；
- **核心规矩**：前端专家绝对不准碰数据库，构建专家只管打包脚本。

---

## 4. 扇出 / 扇入模式 (Fan-out / Fan-in)
并行调研或扫描，随后汇总。
- **适用场景**：跨多个开源项目的选型调研、多日志并发排查。

---

## 5. 监督者模式 (Supervisor)
由中央调度器监控运行状态，动态派发任务和回收上下文。

---

## 6. 协作网络模式 (Collaborative Network)
多智能体点对点对等通信，用于极复杂的开放式创意探索。
